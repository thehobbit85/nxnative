# Android host and cross-target builder parity

The Android release target is the guest-visible behavior available on iOS and macOS. Existing Apple limitations are part of the reference. Record the Apple revision and observed result for each comparison. When Apple implements a feature using a platform-specific API, specify the observable result and the target device capabilities required to reproduce it.

Work in two tracks. In the host, keep Horizon semantics shared and port the underlying OS operations. In graphics, run the same synthetic inputs through NVN on Metal and NVN on Vulkan. Integration steps 1–3 are complete on `codex/cross-platform-runtime`: the remaining donor app/build tools are imported, shared interfaces reconciled, and building and launching validated with synthetic modules. Changes are kept as incremental commits on this branch, with no pull request. The subsequent NSP builder and two-game emulator milestone is complete. The delivery order is builder/extraction/APK packaging, then Android host/loading/Horizon services, then shader translation/export, and finally NVN-to-Vulkan behavioral parity. Each stage must meet its acceptance checks before renderer feature work resumes. Each capability has its own observable test. Run games against fixed scenes for integration, timing and regression measurements. The [NVN command and resource matrix](nvn-vulkan-parity.md) defines the graphics work independently of any title.

**Rebase integration, November 4.** All 74 existing feature commits were replayed on the same branch; it still tracks `fork/codex/cross-platform-runtime`, with no replacement branch or PR. Upstream JIT code memory now uses separate shared RW/RX mappings on Android; synthetic generated instructions execute and update on a second thread on Android and Mac. This does not qualify a commercial JIT game on Android. The shutdown fixture checks the new program-handoff callback on both normal and deadline exits. Shared NRO captures feed the Android rewrite without running Android TLS code in the Mac host. Android movie metadata reports the returned frame's declared color matrix and range. Android filesystem, scheduler, H.264 and metadata fixtures and the corresponding Mac host checks pass. The new Apple sparse-tile release hook owns no resources in Vulkan; sparse residency and physical-tile aliasing remain open renderer work.

**Integration evidence, November 2026.** Vulkan now implements the current recorder's queue activation/finalization and program-forget interfaces. Persistent bindings, render targets and copy strides belong to each queue; finalizing a program clears active and saved queue bindings. Raster origin participates in pipeline-cache identity. The synthetic replay verifies alternating queues and program finalization on an ARM64 Android 15 emulator with SwiftShader. The public transfer fixture now uses `nvnQueueSubmitCommands`, `nvnQueueFinish` and `nvnQueueFinalize`; it passes with both that Vulkan driver and Apple M2 Max Metal, including pixel guards, pitched layers, sync completion and guest timestamp units. This is synthetic coverage, not gameplay evidence. Vulkan has no Apple display-link clock/snapshot ring and uses its existing fallback pacing. Live capture and Metal-specific interactive diagnostic commands remain explicit gaps; native `DM_VK_*` diagnostics are retained.

## Target qualification

1. Define the target manifest and isolate shared preparation behind existing Apple entry points.
2. Land full NDK headless link/bootstrap and explicit capability gaps, with the same synthetic guest and service conformance on Apple and Android.
3. Qualify thread/memory, FS/save/clock behavior, lifecycle, input and media adapters.
4. Build and launch a synthetic APK on hardware, exercising first import, update, suspension and persistence. Develop GPU conformance in parallel, with separate gates for NVN, guest Vulkan and desktop GL.
5. Release each target only at its demonstrated coverage. Use named games as comparative workloads for frame correctness, frame-time percentiles, cold/warm pipeline stalls, memory and stability.
6. Bring up ARM64 Linux against the same suite. Gate Steam Deck separately on translated execution.

## Integration milestone checks

The main NSP/XCI builder routes `--platform android` through shared preparation, validated Vulkan export, a separate Android rewrite and APK packaging. Both commercial workloads now have early-area emulator gameplay and save/reload evidence, linked below. Final packaging verification is complete: both main-builder APKs were installed with their corresponding Android modules and validated shaders; the final packages reload their committed saves and render interactive gameplay. Work remains on the same feature branch with incremental commits and no PR; physical-device qualification and full parity remain separate gates.

Steps 1–3 use the existing branch, not a replacement based on an older fork. The build links the complete current shared host and codecs with the donor frontend and Vulkan executor. `scripts/build_android.py` builds and packages a prepared Android module/shader folder. The reused menu installs bundled assets, writes current cheat-state files, starts NativeActivity and preserves saves on updates. `dm/android/tests/app_fixture.py` builds synthetic NSOs; `app_smoke.py` tests the release-linked path through actual SDK imports and rewritten SVCs rather than supplying alternate host implementations.

Verified locally with NDK r27d, API 30 compilation, an ARM64 Android 15 emulator and SwiftShader: full CLI/shared-library/APK build, SDK startup and nnMain, public NVN submissions and presentation, framework input reaching guest HID, save create/read/write/commit and retention across APK reinstall, pause/resume without restarting the guest, and native-window/swapchain recreation. The public recorded-transfer test also passes on Mac Metal; the current Mac host builds. ELF load segments have 16 KiB alignment; the emulator's kernel uses 4 KiB pages.

The native bionic gate, filesystem, commit-list and save-sync tests pass. The unchanged AAudio suite passed when run with the game paused (24 consecutive renderer blocks, output/release order, disconnect and suspend/resume). During simultaneous emulator activity it observed a callback underrun after three 240-frame blocks, with a 960-frame callback request. This remains an open audio load/driver qualification issue; no audio code was weakened or test assertion removed to obtain a pass.

New Python files pass pinned ruff and pyright checks. The repository-wide Python ratchet still reports the pre-existing optional-regex-match finding at `dm/gfx/tools/dmsh_meshstage.py:101`; that shader-chain file is unchanged by the integration. Targeted LLVM 23.1.4 checks of the changed shared host/public recorder files add no findings. The shared builder regression suite passes 273 tests; the targeted Hollow Knight Apple shader check compares all 1,812 shaders against the pre-milestone revision without changed MSL, interface changes or new failures. That check has no automated gameplay route.

**Commercial emulator evidence, 2026-11-04.** [Hollow Knight](../dm/games/0100633007D48000/README.md#android-integration) renders its player, HUD and world, accepts movement/jump/nail input, commits a save and reloads King's Pass after a process restart.
